# 实验网络部署与换电脑

应用程序可迁移，实验网配置按电脑生成。不能把开发电脑的网卡 GUID、IP、MAC 保留名单、程序安装路径、防火墙规则或租约复制为新电脑的默认配置。仪器用完整型号与序列号核验身份，IP 只是当前连接地址。参见[实验网发现](../architecture/lan-discovery.md)。

## K+K FXE / FXE2：DHCP 与换电脑

后续现场 K+K 统一启用 DHCP。FXE2 支持动态地址；普通交换机本身不分配地址，须由实验网已有 DHCP 或电脑上绑定实验口的服务提供。已登记设备按有效租约中的 MAC 查找当前 IP，再以官方版本查询核对完整型号及序列号；成功后更新原资产地址，不固定当次租约。没有有效租约或身份不符时不访问旧 DHCP 地址，未知租约也不会被猜测为 K+K。首次接入需要先明确目标及当次地址并核验身份。

换电脑时备份库存、设备角色和实机历史，重新选择实际网口、检查 DHCP 服务及组件；不复制旧网卡 GUID、租约或防火墙规则。设备继续使用 DHCP，不为配合旧电脑地址而改回静态。连接与扫描不写网络或测量设置。详细操作与边界见 [K+K 型号卡片](../devices/measurement-analyzers/kplusk-fxe.md)。

项目 `kplusk-config-tool` 和 `scripts/launch-kplusk-config.ps1` 当前对应 **FXE1** 配置工具；FXE2 需要厂家独立的 FXE2 工具，不能混用。FXE2 工具尚未作为已准备组件分发，后续引入须同步下载资源清单。若设备已启用 DHCP，则无需为扫描重新配置固件或网络。官方材料清单见 `deployment/packages/tools/kplusk/README.md`。

如需通过 USB 修改网络，先确认完整型号与序列号，备份原配置，只写授权的网络字段，设备重启后读回。旧 FXE1 的静态流程不代表 FXE2 不支持 DHCP。版本字符串里残留的旧 IP 不作为当前地址依据。LAN 只读连接、重连、参数控制与物理测量分别留档，不把通信通过视为整机验收。

## 安装与环境修复目标

最终安装维护组件携带 DHCP 等离线材料，用户首次选择实验网口后自动完成必要配置；设置内“环境与修复”复用同一执行器。当前只交付检查、方案和报告，执行器后续实现，详见[部署规范](../development/desktop-deployment.md)。

## 两种网络环境

- 网络已有 DHCP（例如实验路由器）：电脑和支持的仪器使用该 DHCP，软件发现并核验新地址，不另开服务器。
- 电脑与仪器只连接普通交换机：交换机不负责分配地址。可以采用明确配置的同网段静态地址、厂商支持的 AutoIP，或由电脑在指定实验有线网口提供 DHCP。

提供 DHCP 时使用通用动态地址池，任意接入该实验网的 DHCP 客户端都可申请；不按型号、序列号或 MAC 白名单准入。地址保留仅用于某些设备需要稳定地址的情况，不能替代通用地址池。Tftpd64 的 `PoolSize=0` 会忽略没有保留地址的请求，且不写常规请求日志；因此“日志没出现设备”不能单独证明线缆不通。依据：[厂商服务源码](https://github.com/PJO2/tftpd64/blob/master/src/_services/bootpd.c)。

## 当前可用的配置准备入口

以下命令只读取本机网络并生成部署方案，不启动 DHCP、不修改地址/防火墙、不扫描仪器或打开 VISA：

```powershell
lab-control-cli network inspect
lab-control-cli network plan --interface "本机实验网卡名称" --plan-file lab-network-plan.json
lab-control-cli network validate --plan-file lab-network-plan.json
```

源码环境可将 `lab-control-cli` 替换为 `.venv-dev\Scripts\python.exe -m lab_control.cli.main`。`inspect` 返回当前物理网卡、地址、默认路由和本机 UDP 67 监听者；没有监听者不等于网络上没有其他 DHCP 服务器。

`plan` 必须指定当前网卡名称或 ID。默认生成 100 个地址、24 小时租期的通用池；按本机现有私有 IPv4 网段计算，不固定任何现场网段。可用 `--server-address` 选择多地址网卡上的现有地址，`--pool-start`、`--pool-size`、`--lease-minutes` 调整范围，重复 `--exclude` 排除已知固定/保留地址。自动计算只避开本机及显式排除地址，尚未探测实际占用；不足时明确报错，不扩大网段。规划拒绝 Wi-Fi、断开的网口及正在通过 DHCP 获取地址的服务端地址。

方案包含本机指纹、当前网卡与网段、路由/DNS/网络类型恢复快照和执行顺序；有默认网关的实验口及与其他接口/VPN 路由冲突的网段会被拒绝。方案，保存在本机运行资料中，不随软件发行。`validate` 遇到另一台电脑、换网卡、地址/前缀变化或方案不一致会拒绝继续，需重新 `inspect` / `plan`。重复写已有方案文件也会拒绝，保留原文件。

## 启用与验证

1. 先确认选中的是实验网口、网络中没有另一台负责同网段分配的 DHCP 服务器，并检查候选池实际占用。排除电脑、网关、仪器固定地址及已有保留地址；启用分配前地址冲突检查。不要凭“没有 ARP 回应”宣称所有关机设备的固定地址均已排除。
2. 在这台电脑安装或定位经批准的 DHCP 运行库。依赖下载遵循[国内镜像与直连规范](../development/environment.md)，不携带开发机的绝对安装路径。
3. 根据方案配置通用池、掩码、租期和所选实验网口绑定；Windows 防火墙按本机可执行文件及网卡限定 DHCP 入站。隔离实验网不填写不存在的互联网网关或 DNS。已有设备的稳定地址保留在池外。
4. 保存服务器配置并核对实际生效值及重启后的值。让仪器重新应用 DHCP；检查 Discover / Offer / Request / ACK，并使用 PyVISA 只读核验完整型号和序列号。连接成功与物理输出验收分开记录。
5. 依据[实机留档规范](../testing/records.md)保存前后配置、哈希、请求/分配证据及身份响应。真实地址、MAC、序列号和报文只保存在运行目录。

目前准备与校验入口已提供；厂商 DHCP 的安装、启用及 Windows 权限步骤仍属于部署操作，未集成为 GUI 一键安装向导。普通启动和“扫描”不会自动启用 DHCP。自动发现支持换电脑，不代表已完成 DHCP 服务自动迁移或实际跨电脑验收。

## 首次安装的网络初始化门禁

首次部署按“确认网络拓扑 → 选择物理实验网口 → 保存前态 → 生成本机地址及服务方案 → 应用并读回 → 验证设备租约与身份”的顺序执行。已有 DHCP 时复用；独立交换机才配置本机 DHCP。当前软件提供检查和方案，尚未集成网络写入执行器；部署人员需完成以下步骤，后续安装器和“环境与修复”须共用这些门禁。不能把开发机的修复脚本或 INI 当成通用初始化配置。

| 初始条件或风险 | 部署处理要求与通过依据 |
| --- | --- |
| 维护操作需要管理员权限 | 提供可见的管理员维护入口；提权失败或被取消要显示，等待须可取消且有超时，不自动重试；普通 GUI 保持普通权限 |
| `%LOCALAPPDATA%` 可能被打包/商店环境重定向 | 按[运行目录与锁规范](../testing/records.md#执行顺序)核对库存、配置、记录和硬件锁的最终物理路径；无法统一时停止硬件 I/O，改用与正式应用一致的执行环境；不创建另一把锁绕过占用 |
| 网卡名称、InterfaceIndex、GUID、MAC 会变化 | 重新枚举已连接物理 Ethernet，让用户确认；不复用旧网卡绑定 |
| WLAN、VPN、虚拟网卡或旧实验设备占用网段 | 同时核对地址与路由，选择不冲突的实验子网；保存既有地址、路由和 DNS，不删除仍服务其他设备的旧配置。现有规划器拒绝默认网关/路由冲突时停止自动应用，先明确处理方案 |
| 实验网卡需要新增地址 | 采用本机验证后的固定服务端地址，核对 ActiveStore、PersistentStore 和地址状态；不能仅凭写入命令成功判断生效，也不自动改 WLAN 默认路由或添加隔离网关 |
| 普通交换机不提供 DHCP | 使用通用池，验证 Discover/Offer/Request/ACK；服务自测和真实设备 ACK 分开显示 |
| 系统 DHCP-In 规则只覆盖客户端端口 68 | 按当前服务路径和选定网卡创建 UDP 67、远端 68 规则，保存并读回前后规则 |
| Tftpd64 默认可能启用多项服务或 `PoolSize=0` | 只启用 DHCP (`Services=4`)，池大小大于 0，Gateway/DNS 为空，并读回实际配置 |
| DHCP 池与已知固定设备地址重叠 | 排除电脑地址、固定设备地址及保留地址；同时核查现有租约和冲突探测，禁止用旧开发机租约初始化新电脑 |
| 同一物理网卡具有多个 IPv4 地址 | 分别确定 DHCP 收包接口地址、服务端应答地址和地址池子网；不能假定三者都是同一个地址，按下节验证绑定及实际报文 |
| 服务读取的配置与 GUI 展示的配置不同 | 核实服务可执行文件、版本、启动方式和实际 INI 来源（包括 `TFTP_INI`）；保存原文件及哈希，修改后重启该服务并读回；仅保存 GUI 设置不能作为服务生效证据 |
| 设备可能不会立即续租 | 安装完成后提示重新应用 DHCP；需要重新上电/重插网线时先结束采集并保存设备状态，等待租约变化后再扫描 |
| DHCP 正常但设备不广播 VXI-11/mDNS | 首次按当前地址和仪器公布端口核验完整身份，启用地址跟随后由[本机租约发现](../architecture/lan-discovery.md#本机-dhcp-租约发现)关联 MAC；后续每轮读取有效租约并重新核验身份，不把初始 IP 写成固定连接要求 |
| 失败时可能破坏用户网络 | 维护进程持有硬件锁，保存地址、DHCP、DNS、路由、服务、防火墙快照；只回滚本应用拥有且未被外部修改的内容，不自动重启 |

### Tftpd64 多地址网卡绑定

使用已登记的 Tftpd64 Service 4.74 时，部署人员需核查 `[TFTPD32]` 中的 `LocalIP` 和 `DHCP LocalIP`，不能只看 GUI 顶部的 Server interfaces。`DHCP LocalIP` 是 DHCP 接收接口的筛选地址；同一网卡添加第二个实验子网地址后，Windows 上报的接收接口地址仍可能是该网卡原来的 IPv4 地址。若将筛选值直接设为新增地址，服务可以正常运行并监听 UDP 67，却把请求记为 `Message received on an unbound interface` 并丢弃。

初始化时从选定的物理网卡及实际接收信息确定 `DHCP LocalIP`，只允许使用该网卡当前拥有的地址；`LocalIP` 和 `[DHCP]` 的 `IP_Pool`、`Mask` 则按所选实验子网配置。不得为消除报错而取消接口限制、绑定所有网络或覆盖其他网卡设置。单地址网卡通常无需区分这两个地址；多地址网卡必须做真实报文自测，不能把这一版本的本机观察当作所有版本的固定行为。配置键及服务端地址选择逻辑参见[官方设置定义](https://github.com/PJO2/tftpd64/blob/master/src/_common/settings.h)和[官方 DHCP 实现](https://github.com/PJO2/tftpd64/blob/master/src/_services/bootpd.c)；升级组件后重新验收。

保存并重启服务后，验证 OFFER 的来源地址、Server Identifier、分配地址和掩码符合实验子网，且请求不再因接口绑定被拒绝。临时诊断客户端的 OFFER 只能证明服务应答，不能替代目标仪器的 REQUEST/ACK。自测所用标识、报文和临时租约留在本机维护记录，不写入发行配置。

### 设备接入验收

| 阶段 | 首次部署通过依据 | 不能代替的后续检查 |
| --- | --- | --- |
| 服务和防火墙 | 指定服务运行、UDP 67 监听、仅实验网口放行、配置读回一致 | 服务能够正确分配地址 |
| DHCP 协议 | 本机 OFFER 内容正确；目标设备有对应 MAC 的有效租约及 REQUEST/ACK 证据或可核验的租约开始时间 | 仪器型号和序列号核验 |
| 网络可达 | 设备显示有效非零 IP，同网段通信可达，ARP MAC 与选定设备一致；不以 Ping 无响应单独判定故障 | SCPI/VISA 通信 |
| 应用连接 | 使用设备公布的协议/端口，通过 PyVISA 只读读取完整型号、序列号并完成兼容层连接；保存到正式应用运行目录 | 参数控制、恢复和物理性能验收 |

RIGOL DHO900 系列在 Utility 的 LAN 页面启用 DHCP 后，应点击底部 **Apply** 使设置生效；DHCP、Auto IP、Static IP 同时启用时优先级依次降低。`connected` 或 LAN 灯亮但 IP 为 `0.0.0.0`、VISA 主机字段为空时，尚未具备可用远程地址，应先完成地址分配验收。依据：[DHO900 官方用户手册，Network Setting](https://www.rigol.com/dam/global/downloads/brochures/en/user-manual/oscilloscopes/DHO900_UserGuide_EN.pdf)。取得有效地址后按[本项目 DHO924 连接要求](../../src/lab_control/instruments/devices/rigol_dho924/README.md#连接与驱动)选择仪器自报 Socket 端口；地址更新不代表所有 VISA 协议均已验证。

组件只有在干净 Windows 10/11 电脑完成离线安装、管理员维护、电脑重启后地址/服务恢复和真实设备验收后才可从 `pending` 变为 `verified`。首次安装、重复修复、已有多地址网卡、已有固定地址设备、拒绝提权和失败恢复都需覆盖；单台开发机成功不能代替交付验收。

部署验收还须区分地址分配与地址跟随：本机 Tftpd64 的通用池不为某台仪器写死 IP；已登记资产通过 MAC 定位当前租约、以完整身份核验新地址。原始租约和旧电脑服务绑定不迁移，已有资产的 MAC/身份关联可随库存保留，但换电脑仍须重新配置本机 DHCP 并验证实际通信。当前只对已核验的 VISA LAN 资源进行租约跟随；未知 Socket 设备首次需确认端口，外部 DHCP 服务器需其自身的发现或租约接入机制。

## 迁移边界

可以迁移需要保留的资产名称、槽位、实验限值及历史记录；连接地址重新发现后核验。新电脑重新安装相应 VISA/厂商运行库，选择实验网口并生成本机配置。不要迁移旧租约、旧网卡绑定、另一台电脑的计划任务或防火墙规则；旧部署方案仅作为审计记录。
